# 2. Contract 1 — Frontend to API

Login uses:

```js
axiosInstance.post('/users/login', form)
```

Signup uses:

```js
axiosInstance.post('/users/register', form)
```

The frontend needs to know:

```text
URL
method
request body
credentials policy
response shape
error shape
```

The backend needs to provide exactly that contract.

For example, registration expects:

```json
{
  "name": "Rahul",
  "username": "rahul123",
  "email": "rahul@example.com",
  "password": "secret"
}
```

The backend validates those fields before doing database work.

That is the API boundary.

---

# 3. Contract 2 — Backend to Browser

After successful login/register, the server does two things:

```text
1. Return user information
2. Set authentication cookie
```

The browser therefore receives something conceptually like:

```http
Set-Cookie: token=...
```

and JSON:

```json
{
  "message": "Login successful",
  "user": {
    "_id": "...",
    "name": "Rahul",
    "username": "rahul123",
    "email": "rahul@example.com"
  }
}
```

Those two outputs have different responsibilities.

```text
Cookie -> future authentication
JSON   -> immediate UI state
```

Do not merge them mentally.

---

# 5. Contract 4 — JWT signing and verification

The token utility creates the JWT.

The middleware verifies the JWT.

Both must use the same secret:

```text
generateToken()
      |
      v
JWT_SECRET
      |
      v
jwt.sign()

          later

jwt.verify()
      |
      v
JWT_SECRET
```

The recent fixes around the environment-variable name are therefore not cosmetic.

A single mismatch can make every valid session look invalid.

This is a great example of an **integration bug masquerading as a logic bug**.

---

# 6. Contract 5 — JWT to current user

The JWT contains the user identity claim, such as:

```js
{ userId }
```

After verification:

```js
const decoded = jwt.verify(token, process.env.JWT_SECRET)
```

we use:

```js
const user = await User.findById(decoded.userId)
```

Then:

```js
req.user = user
```

The controller now gets authenticated user context without needing to know anything about cookie parsing or cryptographic verification.

This is separation of concerns:

```text
Middleware
  -> authenticate

Controller
  -> perform business operation
```

---

# 7. Why `select('-password')` matters

The middleware currently loads:

```js
const user = await User.findById(decoded.userId)
  .select('-password')
```

This means the password field is deliberately excluded from the authenticated request user.

That gives us an additional safety boundary.

Even if:

```js
req.user
```

is later returned by a controller, the password field does not come along from that query.

Defence in depth is the bigger lesson.

Do not rely on only one place to remember:

> “Oh yes, we must not return password.”

Instead, shape the data so accidental leakage becomes harder.

# 8. Authentication initialization is a boot process

When React starts:

```text
React application
      |
      v
AuthProvider
      |
      v
loading = true
      |
      v
GET /users/me
```

The backend decides whether the existing browser credential is valid.

Then React reaches one of two final states:

```text
authenticated
or
unauthenticated
```

This can be viewed as an application boot process:

```text
BOOT
 ↓
RESTORE SESSION
 ↓
RESOLVE AUTH
 ↓
RENDER ROUTES
```

That pattern appears in many real applications.

---

# 9. Why `loading` is a real state, not a UI detail

Suppose `loading` did not exist.

React would only see:

```js
user = null
```

and have no way to distinguish:

```text
“I know the user is logged out.”
```

from:

```text
“I haven't checked yet.”
```

The result is often:

```text
refresh
 ↓
login redirect
 ↓
/me succeeds
 ↓
user found
```

That creates a flash or redirect race.

So:

```text
loading = true
```

is a real domain state.

It is not merely a spinner toggle.

---

# 10. Public and protected routes are policy objects

The route wrappers are effectively two policies.

## Protected

```text
authenticated -> allow
unauthenticated -> redirect
unknown -> wait
```

## Public

```text
unauthenticated -> allow
authenticated -> redirect
unknown -> wait
```

Writing the rules in plain English before writing the code is a powerful technique.

Then the implementation becomes almost mechanical.

---

# 11. Why route decisions must happen after auth resolution

A good route guard follows this order:

```js
const { user, loading } = useAuth()

if (loading) {
  return <Loading />
}

if (!user) {
  return <Navigate to="/login" replace />
}

return children
```

Not:

```js
if (!user) {
  return <Navigate ... />
}

const { user, loading } = useAuth()
```

The second form violates hook rules.

The first form preserves:

```text
same hooks
same order
every render
```

---

# 12. `useAuth()` should be boring

The hook itself is intentionally tiny:

```js
export const useAuth = () => useContext(AuthContext)
```

That is good.

A custom hook does not need to be complicated to be useful.

It gives the rest of the application a readable abstraction:

```js
const { user, loading } = useAuth()
```

instead of repeatedly writing:

```js
useContext(AuthContext)
```

The abstraction also gives us one place to evolve the API later.

---

# 13. What happens if the backend is down?

This scenario is worth understanding.

AuthContext calls:

```js
GET /users/me
```

If the backend is unavailable, the request fails.

The current client then moves toward:

```text
user = null
loading = false
```

From the UI's perspective this may look identical to “logged out.”

That is a useful teaching point: **authentication state and server availability are not the same domain concept**.

A more sophisticated application may distinguish:

```text
checking
authenticated
unauthenticated
session-check-error
```

For this project stage, keeping the model simple is reasonable, but students should recognize the trade-off.

---

# 14. Error messages are also API contracts

The backend might return:

```json
{
  "message": "Invalid credentials"
}
```

The frontend uses:

```js
error.response?.data?.message
```

This is another contract.

If the backend suddenly changes from:

```json
{ "message": "Invalid credentials" }
```

to:

```json
{ "errorText": "Invalid credentials" }
```

then the frontend fallback will trigger.

That might not crash the app, but it changes the user experience.

Again:

> API contracts include error responses, not just successful responses.

---

# 15. Normalising email at the API boundary

Registration normalises:

```js
const normalizedEmail = email.trim().toLowerCase()
```

and login searches using the same approach.

That gives us consistent behaviour for values such as:

```text
User@Example.com
 user@example.com 
USER@EXAMPLE.COM
```

The general engineering principle is:

> Normalise data at the boundary so the rest of the system can rely on consistent values.

If registration stores one representation and login searches for another, users get confusing “invalid credentials” behaviour despite entering the same logical email.

---

# 16. Duplicate checks vs database constraints

The controller checks:

```js
User.findOne({ username })
```

and:

```js
User.findOne({ email: normalizedEmail })
```

This is useful for friendly API responses.

But students should understand a deeper database lesson:

> An application-level check is not the same as a database uniqueness guarantee.

Two concurrent requests can theoretically both pass a preceding `findOne()` check.

For production systems, important uniqueness requirements should also be enforced with database-level indexes/constraints.

This teaches the distinction between:

```text
validation
vs
integrity guarantee
```

# 18. Security hygiene — what should never happen

Never:

```text
commit real JWT secrets
commit real database credentials
return password hashes unnecessarily
log plaintext passwords
put secrets in JWT payloads
trust an unverified JWT payload
rely only on frontend route guards
```

And remember:

```text
.env in .gitignore
```

is good hygiene but does not erase secrets that have already been committed.

Once a credential has been exposed, treat it as compromised and rotate it.


Suppose it says:


```text
React context architecture
```

Not:


# 22. Example: login returns 200 but refresh fails

Before refresh:

```text
Login -> 200
Home -> visible
```

After refresh:

```text
Home -> login
```

This points strongly toward session restoration.

Check:

```text
Does /users/me run?
Does it return 200?
Is cookie included?
Is withCredentials enabled?
Does AuthContext call setUser?
Does loading become false?
```

Notice how the symptom already narrows the search area.

That is diagnostic reasoning.

# 23. Example: every login is suddenly invalid

Imagine no code changed except a `.env` edit.

Symptoms:

```text
Login credentials are correct
JWT cookie exists
/users/me -> 401
```

First suspect:

```text
JWT configuration
```

Check:

```text
JWT_SECRET exists
same name everywhere
same environment loaded
server restarted
```

The commit history contains exactly this class of issue.

It is why environment configuration belongs in our debugging knowledge, not just deployment knowledge.

# 24. Authentication and authorization are different

Our current work is primarily authentication:

```text
Who are you?
```

Authorization comes next:

```text
Are you allowed to perform this action?
```

For example:

```text
Authentication
-> req.user = user123

Authorization
-> Is user123 allowed to delete post456?
```

A protected route only establishes authenticated access.

A future post/comment/follow system will need authorization decisions as well.

This distinction becomes increasingly important as the social-media application grows.

---

# 25. Why this architecture is ready for the next features

Now that authentication is centralised, future pages can assume:

```js
const { user } = useAuth()
```

instead of rebuilding session logic.

Future backend routes can assume:

```js
isAuthenticated
```

instead of copying token-verification code.

This creates reusable infrastructure.

That is the payoff of architecture.

You pay the complexity once so future features become cheaper.
