# What we are solving today

Before today's work, the backend could authenticate a user, but the frontend still needed a clean way to say:

> “I am logged in. Here is my current user. Keep me logged in while I move around the application.”

There are three separate problems hiding inside that sentence:

```text
1. How does the frontend send credentials to the backend?
2. How does the browser send the authentication cookie automatically?
3. How does React remember the authenticated user after a page refresh?
```

The architecture we are moving toward is:

```text
React UI
   |
   | Axios request
   v
Express API
   |
   | login/register
   v
JWT -> HttpOnly Cookie
   |
   | browser stores cookie
   v
future request
   |
   v
/ users / me
   |
   v
JWT verification
   |
   v
req.user
   |
   v
JSON user response
   |
   v
AuthContext
   |
   v
Protected/Public routes
```

The key insight is that **the cookie is the browser's credential, while React state is the UI's representation of authentication state**.

These are related, but they are not the same thing.

# Part 1 — The browser-to-backend connection

## 1. Why use a shared Axios instance?

Instead of writing this repeatedly:

```js
axios.post('http://localhost:8084/users/login', data)
axios.post('http://localhost:8084/users/register', data)
axios.get('http://localhost:8084/users/me')
```

we create one configured Axios client:

```js
import axios from 'axios'

const axiosInstance = axios.create({
   baseURL: 'http://localhost:8084',
   withCredentials: true,
   headers: {
     'Content-Type': 'application/json'
   }
})

export default axiosInstance
```

This gives us a single place for common HTTP configuration.

Think of `axiosInstance` as our application's dedicated courier service.

Every department can say:

```text
“Send this request to the backend.”
```

without separately remembering the server address and authentication-cookie rules.

## 2. `baseURL`

We configure:

```js
baseURL: 'http://localhost:8084'
```

Therefore:

```js
axiosInstance.post('/users/login', form)
```

becomes:

```text
POST http://localhost:8084/users/login
```

This becomes especially useful when the environment changes.

Today:

```text
localhost
```

Later:

```text
staging API
production API
```

The application should not have backend URLs scattered across twenty files.

# Part 2 — Why `withCredentials` is critical

## 3. The cookie problem

Our authentication design uses a cookie:

```js
res.cookie('token', token, cookieOptions)
```

The browser is responsible for storing the cookie.

But when the frontend is running on:

```text
http://localhost:5173
```

and the API is running on:

```text
http://localhost:8084
```

we are dealing with different origins.

Axios must be told that credentials are part of the request configuration:

```js
withCredentials: true
```

Without this, you can have the frustrating situation where:

```text
Login API -> 200 OK
Cookie -> created

but later:
GET /users/me -> 401
```

Students often conclude that JWT is broken.

It is not.

The real problem is usually that the browser did not include the cookie with the later request.

## 4. Credentials require cooperation from both sides

Frontend:

```js
withCredentials: true
```

Backend:

```js
cors({
    origin: 'http://localhost:5173',
    credentials: true
})
```

The current backend configuration follows that model. fileciteturn18file0

The rule to remember is:

```text
Frontend says:
“I am allowed to send credentials.”

Backend says:
“I accept credentialed requests from this exact origin.”
```

If either side is configured incorrectly, authentication can appear to work for one request and mysteriously fail for the next.

# Part 3 — Registration from React

## 5. Controlled form state

The Sign Up page stores:

```js
const [form, setForm] = useState({
  name: '',
  email: '',
  username: '',
  password: ''
})
```

Every input is controlled by React:

```js
value={form.name}
onChange={handleChange}
```

The generic change handler is:

```js
const handleChange = (e) => {
  setForm((prev) => ({
    ...prev,
    [e.target.name]: e.target.value
  }))
}
```

This is a very important JavaScript + React pattern.

If the input has:

```html
name="email"
```

then:

```js
e.target.name
```

is:

```text
email
```

and the update becomes conceptually:

```js
setForm({
  ...prev,
  email: 'new value'
})
```

Notice why the spread operator matters.

Without:

```js
...prev
```

you would accidentally replace the whole object with one field.

# Part 4 — Sending the registration request

## 6. `preventDefault()`

The form handler starts with:

```js
const handleSubmit = async (e) => {
  e.preventDefault()
```

A `<form>` normally wants to perform the browser's default submission behavior.

For a React application, we usually want JavaScript to take over:

```text
user submits form
      |
      v
React handler runs
      |
      v
prevent browser navigation
      |
      v
send API request manually
```

If you forget `e.preventDefault()`, the browser may navigate/reload before your React flow behaves as expected.

## 7. Loading state

We use:

```js
setLoader(true)
```

before the request and:

```js
setLoader(false)
```

inside `finally`.

This gives us a reliable state machine:

```text
idle
  |
  | submit
  v
loading
  |
  +---- success ---> done
  |
  +---- failure ---> error
  |
  +---- finally ---> loading=false
```

The `finally` block is powerful because it runs after both success and failure.

# Part 6 — Why CORS appears suddenly

## 9. What is CORS?

A browser is not allowed to freely make every cross-origin request with every capability.

Our frontend and backend run on different origins:

```text
Frontend: http://localhost:5173
Backend:  http://localhost:8084
```

The backend explicitly enables the frontend origin:

```js
app.use(cors({
    origin: 'http://localhost:5173',
    credentials: true
}))
```

This tells the browser that the API is willing to participate in this cross-origin interaction.

## 10. Common CORS mistake #1

Do not casually replace:

```js
origin: 'http://localhost:5173'
```

with:

```js
origin: '*'
```

when you are using credentials.

Credentialed cross-origin requests require a concrete allowed origin, not a wildcard.

The important classroom pairing is:

```text
cors origin
+
credentials: true
+
axios withCredentials: true
+
cookie settings
```

All four pieces need to make sense together.

# Part 7 — Sign Up navigation

## 11. Why navigate after registration?

The Sign Up page currently does:

```js
await axiosInstance.post('/users/register', form)
navigate('/login', { replace: true })
```

The intention is deliberately simple for this teaching stage:

```text
registration successful
        |
        v
move to Login
```

We are not inventing extra product behavior here.

The important concept is that **navigation should happen only after the awaited API request succeeds**.

This is why the placement matters.

Wrong:

```js
navigate('/login')
await axiosInstance.post('/users/register', form)
```

Correct:

```js
await axiosInstance.post('/users/register', form)
navigate('/login')
```

The first version can navigate even when registration fails.

# Part 8 — Login is different from Sign Up

## 12. Login has two outputs

A login request does not merely return data.

It creates authenticated browser state.

The backend does:

```js
const token = generateToken(user._id)
res.cookie('token', token, cookieOptions)
```

and returns a sanitized user object. fileciteturn13file0

So one HTTP response carries two important things conceptually:

```text
Response
  |
  +--> Set-Cookie: token=...
  |
  +--> JSON: user information
```

This distinction is extremely important.

### Cookie

Used for authentication on future requests.

### JSON user

Used by the React application to immediately render the authenticated UI.

They solve different problems.

# Part 10 — Why AuthContext exists

Suppose ten components need the current user:

```text

      ├── Navbar
      │    └── UserMenu
      ├── Home
      │    ├── Feed
      │    └── Sidebar
      └── Profile
```

Passing:

```js
user
```

through every level becomes annoying.

React Context lets us create a shared authentication state.

Our project creates:

```js
const AuthContext = createContext()
```

and then an:

```js

```

around the application. fileciteturn10file0

```js
const { user } = useAuth()
```

# Part 11 — The most important AuthContext state

## 14. Why two states: `user` and `loading`?

The context maintains:

```js
const [user, setUser] = useState(null)
const [loading, setLoading] = useState(true)
```

At first glance, beginners often think:

```text
user = null
```

means:

```text
logged out
```

But during application startup, that conclusion may be wrong.

Imagine this sequence:

```text
page refresh
   |
   v
React starts
   |
   v
user = null
   |
   v
request /users/me
   |
   v
server checks cookie
   |
   v
user found
   |
   v
setUser(realUser)
```

During the request, `user === null` did **not** mean the user was logged out.

It meant:

> “We have not finished checking yet.”

That is exactly why we need:

```js
loading
```

So authentication has three conceptual states:

```text
loading = true  -> unknown
loading = false + user = null -> logged out
loading = false + user != null -> logged in
```

This mental model is essential for protected routes.

# Part 12 — Rehydrating authentication with `/users/me`

## 15. What happens on a refresh?

React state normally disappears when the browser performs a full page reload.

The cookie does not disappear merely because React restarted.

So after booting the application we ask the backend:

```js
const response = await axiosInstance.get('/users/me')
```

The browser automatically includes the authentication cookie because the Axios instance is configured with:

```js
withCredentials: true
```

The backend route is protected:

```js
userRoutes.get('/me', isAuthenticated, getMe)
```

and the middleware verifies the token and loads the current user. fileciteturn19file0 fileciteturn14file0

The frontend then does:

```js
setUser(response.data)
```

This process is called **authentication rehydration**.

The simplest mental model is:

```text
Cookie survives
      |
      v
React restarts
      |
      v
React asks server:
“Who am I?”
      |
      v
/users/me
      |
      v
server verifies cookie
      |
      v
server returns current user
      |
      v
AuthContext restores user state
```

# Part 13 — Why `/users/me` is better than trusting stale client state

Suppose the browser had this state before refresh:

```js
{
  name: 'Rahul',
  username: 'rahul123'
}
```

But the profile was later changed on the server.

The backend is the source of truth for current user state.

That is why `/users/me` exists.

It answers:

> “Given the authentication credential currently attached to this browser, who is the current user according to the server?”

That is more reliable than trying to rebuild identity entirely from frontend storage.

# Part 14 — Preventing race-condition style warnings in AuthContext

## 16. Why the `mounted` flag exists

The context uses:

```js
let mounted = true
```

and later:

```js
return () => {
  mounted = false
}
```

then checks:

```js
if (mounted) {
  setUser(...)
}
```

and:

```js
if (mounted) {
  setLoading(false)
}
```

The purpose is to avoid trying to update state after the effect has been cleaned up.

The broader React lesson is more important than the exact flag:

> Async work may finish later than the component/effect that started it.

That means you have to think about lifecycle and cleanup whenever an effect performs asynchronous work.

# Part 15 — Public vs Protected routes

## 17. What is a protected route?

A protected route means:

> “Only authenticated users should be allowed to render this page.”

Our current routing uses:

```jsx
<Route
  path='/home'
  element={
    <ProtectedRoute>
      <Home />
    </ProtectedRoute>
  }
/>
```

The route itself does not understand authentication.

The wrapper does.

The current `ProtectedRoute` reads:

```js
const { user, loading } = useAuth()
```

then follows the three-state model:

```js
if (loading) {
  return <h1>Loading...</h1>
}

if (!user) {
  return <Navigate to='/login' replace />
}

return children
```

The logic is:

```text
loading?
  |
  +--> yes -> wait
  |
  no
  |
  v
user exists?
  |
  +--> no -> login
  |
  yes
  |
  v
render protected page
```

This order matters.

# Part 16 — The famous Hooks bug

## 18. Why “change in order of Hooks” happens

One of the real debugging milestones from this project was the React warning:

```text
React has detected a change in the order of Hooks called by ProtectedRoute.
```

This is not a cosmetic warning.

React relies on hooks being called in the same order on every render.

Wrong pattern:

```js
if (loading) {
  return <Loading />
}

const { user } = useAuth()
```

On one render, `useAuth()` may not run.

On another render, it does run.

That means the hook order changes.

Correct pattern:

```js
function ProtectedRoute({ children }) {
  const { user, loading } = useAuth()

  if (loading) {
    return <Loading />
  }

  if (!user) {
    return <Navigate to='/login' replace />
  }

  return children
}
```

All hooks happen before conditional returns. fileciteturn11file0

### Rule of thumb

> Never conditionally call hooks.

You can conditionally render after hooks have been called.

# Part 17 — PublicRoute

## 19. Why do we need the opposite of ProtectedRoute?

Suppose the user is already logged in.

Should they manually type:

```text
/login
```

and see the login page again?

Usually no.

The current `PublicRoute` handles exactly that case:

```js
if (loading) {
  return <p>Loading...</p>
}

if (user) {
  return <Navigate to='/home' />
}

return children
```

So:

```text
not logged in -> login/signup can render
logged in     -> redirect to home
```

The application therefore has two route policies:

```text
PublicRoute
    “Guest users may enter.”

ProtectedRoute
    “Only authenticated users may enter.”
```

The root application currently has:


# Part 19 — Backend consistency matters

## 20. One environment variable name everywhere

Authentication can fail even when the code is otherwise correct if different files use different environment variable names.

The project now converges on:

```text
JWT_SECRET
```

The environment template is:

```env
dbURL=your-mongodb-connection-string
JWT_SECRET=your-jwt-secret
```

The middleware verifies with:

```js
jwt.verify(token, process.env.JWT_SECRET)
```

and the token utility should sign with the same secret. fileciteturn20file0 fileciteturn14file0

### The bug this prevents

```text
sign with SECRET_A
verify with SECRET_B
```

Every token then looks invalid.

The browser may have a perfectly valid-looking cookie, but the server cannot verify it.

This is a classic configuration bug that looks like an authentication bug.

# Part 20 — The server middleware contract

The final middleware is now conceptually:

```js
const isAuthenticated = async (req, res, next) => {
  try {
    const token = req.cookies.token

    if (!token) {
      return res.status(401).json({ message: 'Login required' })
    }

    const decoded = jwt.verify(token, process.env.JWT_SECRET)

    const user = await User.findById(decoded.userId)
      .select('-password')

    if (!user) {
      return res.status(401).json({ message: 'User not found' })
    }

    req.user = user
    next()
  } catch (err) {
    return res.status(401).json({
      message: 'Invalid or expired token'
    })
  }
}
```

Notice the important improvements:

```text
missing token  -> stop immediately
invalid token  -> 401
missing user   -> 401
password field -> excluded
success        -> req.user + next()
```

This is much cleaner than a middleware that sends an error and then continues executing.

# Part 21 — Logout

## 21. Logout is not “delete React state”

A common beginner implementation is:

```js
setUser(null)
```

and nothing else.

That changes the UI but does not necessarily invalidate the browser's authentication cookie.

The project uses a backend endpoint:

```js
userRoutes.post('/logout', isAuthenticated, logoutUser)
```

and the controller clears the cookie. fileciteturn19file0 fileciteturn13file0

The frontend logout function then does:

```js
try {
  await axiosInstance.post('/users/logout')
} finally {
  setUser(null)
}
```

Now we have two synchronized changes:

```text
server auth state -> cookie cleared
frontend auth state -> user cleared
```

This is the correct way to think about logout in our cookie-based design.

# Part 22 — Logout route design discussion

One interesting design question is whether logout itself needs authentication middleware.

The current project uses:

```js
userRoutes.post('/logout', isAuthenticated, logoutUser)
```

That works because only an authenticated request is considered a valid logout request.

An alternative design can make logout idempotent and clear the cookie even if the cookie is already missing/expired.

The important engineering lesson is not that one route shape is universally correct.

It is:

> Decide the semantics deliberately.

A good logout endpoint should reliably leave the browser in a logged-out state.

# Part 23 — Common bugs you should expect

## Bug 1 — Login succeeds but `/users/me` says 401

Check these in order:

```text
1. Is the server setting the cookie?
2. Does Axios use withCredentials: true?
3. Does CORS use credentials: true?
4. Does CORS allow the exact frontend origin?
5. Is cookie SameSite compatible with your setup?
6. Is the JWT secret identical for sign + verify?
7. Is cookie-parser installed before the route handlers?
```

The backend currently installs:

```js
app.use(cookieParser())
```

before routing, so `req.cookies` is available to the auth middleware. fileciteturn18file0

## Bug 2 — “No token Found” even though login worked

Open browser DevTools.

Inspect the request/response and cookie storage.

Do not debug authentication only from React console logs.

Authentication is a browser + network + backend problem.

Use:

```text
Browser DevTools
    |
    +--> Network
    +--> Application/Storage -> Cookies
    +--> Request headers
    +--> Response headers
```

## Bug 3 — CORS error in browser console

Check:

```js
origin: 'http://localhost:5173'
credentials: true
```

and frontend:

```js
withCredentials: true
```

Also make sure you are not accidentally visiting the frontend using a different origin such as:

```text
http://127.0.0.1:5173
```

while the backend only allows:

```text
http://localhost:5173
```

Those are not the same origin.

## Bug 4 — `useAuth()` returns the wrong value

Check that:

```jsx
<AuthProvider>
  ...
</AuthProvider>
```

wraps the consumers.

Remember:

```text
Provider outside consumer
```

not:

```text
Consumer outside provider
```

## Bug 5 — Redirect happens too early

This often comes from forgetting the `loading` state.

Bad mental model:

```text
user === null -> redirect immediately
```

Correct mental model:

```text
loading -> wait
then
user null -> redirect
user exists -> render
```

## Bug 6 — Hooks warning in ProtectedRoute/PublicRoute

Search for hooks such as:

```js
useAuth()
useEffect()
useState()
useNavigate()
```

being called inside conditions, loops or nested functions.

Hooks must preserve the same order on every render.

## Bug 7 — Registration succeeds but login immediately fails

Possible causes:

```text
email normalization mismatch
password hash not stored correctly
wrong database/environment
backend using different JWT secret
frontend calling wrong API URL
```

The current registration/login controllers normalize emails consistently. fileciteturn13file0

## Bug 8 — “It works after login, but refresh logs me out”

That usually means the frontend has only local React state and has not implemented authentication rehydration.

The fix is:

```js
useEffect(() => {
  axiosInstance.get('/users/me')
}, [])
```

which the current AuthContext now performs. fileciteturn10file0

# Part 24 — How to debug the entire system systematically

Do not randomly change code.

Debug the pipeline from left to right.

## Step 1 — Browser

Ask:

```text
Did the form handler run?
```

## Step 2 — Network

Ask:

```text
Did POST /users/login happen?
```

## Step 3 — Backend controller

Ask:

```text
Did the user exist?
Did password comparison return true?
Did generateToken run?
Did res.cookie run?
```

## Step 4 — Response

Ask:

```text
Did the response contain Set-Cookie?
```

## Step 5 — Browser cookie jar

Ask:

```text
Was the cookie actually stored?
```

## Step 6 — Future request

Ask:

```text
Does GET /users/me contain the cookie?
```

## Step 7 — Backend middleware

Ask:

```text
Did req.cookies.token exist?
Did jwt.verify succeed?
Did User.findById succeed?
```

## Step 8 — React state

Ask:

```text
Did setUser run?
Is AuthContext mounted?
Is loading resolved?
```

## Step 9 — Routing

Ask:

```text
Did ProtectedRoute see user?
```

This method prevents ten random fixes for one simple configuration error.

# Part 26 — Engineering lessons from today's commits

Today's commit history contains a surprisingly important lesson: **integration work is often harder than writing the individual feature**.

We already knew how to write:

```text
bcrypt
JWT
middleware
cookies
```

But the actual application still failed when:

```text
environment names did not match
frontend requests lacked credentials
CORS did not allow the origin
React state did not rehydrate
route guards rendered too early
hooks were called conditionally
```

This is real full-stack engineering.

A system is not “done” because every individual file looks correct.

The system is done when the pieces agree on their contracts.

The contracts are:

```text
Frontend <-> HTTP
HTTP <-> CORS
Browser <-> Cookie
Cookie <-> JWT
JWT <-> Secret
JWT <-> MongoDB user
Backend <-> AuthContext
AuthContext <-> Route Guards
```
