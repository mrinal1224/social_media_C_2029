# Part 1 — JWT generation

## 1. Why do we need a token?

HTTP is stateless. The server receives independent requests unless we explicitly carry some authentication state between them.

A JWT gives us a compact, signed representation of an identity claim that the server can verify later.

Think of it like a signed visitor pass:

```text
Visitor ID -> 12345
Valid until -> tomorrow
Signed by security -> yes
```

The pass is not the original password. It is evidence that the server issued an authenticated credential for that identity.

## 2. The JWT utility

We introduced:

```text
backend/utils/genToken.js
```

with:

```js
import jwt from 'jsonwebtoken'

const genToken = (userId) => {
    return jwt.sign(
        { userId },
        process.env.jwt_secret,
        { expiresIn: '7d' }
    )
}

export default genToken
```

The reason I want this in a utility instead of duplicating it inside register/login is simple: token creation is one reusable concern.

If we later change expiration, claims, or signing configuration, there is one central place to update.

## 3. Understanding `jwt.sign()`

The function is conceptually:

```js
jwt.sign(payload, secret, options)
```

Our three inputs are:

```js
{ userId }
```

```js
process.env.jwt_secret
```

and:

```js
{ expiresIn: '7d' }
```

### Payload

Because of JavaScript shorthand:

```js
{ userId }
```

means:

```js
{ userId: userId }
```

We keep the claim small. We do not want to duplicate the entire user document inside the token.

### Secret

The signing secret comes from the environment:

```js
process.env.jwt_secret
```

Never hardcode a production authentication secret into source code.

### Expiry

The project currently uses:

```js
expiresIn: '7d'
```

That is a classroom-friendly lifetime. Production systems may use shorter access-token lifetimes combined with refresh tokens.

## 4. JWT is not encryption

A common mistake is to think:

> “The JWT payload is safe because it is encoded.”

It is not a confidentiality mechanism.

A JWT is normally structured as:

```text
HEADER.PAYLOAD.SIGNATURE
```

The header and payload can be read by anyone who has the token. The signature is what provides integrity/authenticity under the chosen signing scheme.

So never put this into a normal JWT payload just because the token is “secure”:

```json
{
  "password": "secret"
}
```

Keep sensitive secrets out of the payload.

# Part 2 — Using JWT after registration and login

## 5. Registration changes

After creating the new user:

```js
const newUser = await User.create({
    username,
    name,
    password: hashedPassword,
    email
})
```

we generate:

```js
const token = genToken(newUser._id)
```

The request therefore becomes:

```text
register
  -> validate
  -> hash password
  -> create user
  -> take MongoDB _id
  -> generate JWT(userId)
```

The token represents the database identity instead of duplicating all user data.

## 6. Login changes

Login follows the same pattern after password verification:

```js
const correctPassword = bcrypt.compareSync(
    password,
    userExists.password
)
```

If correct:

```js
const token = genToken(userExists._id)
```

Again, the JWT carries the user identity claim.

# Part 3 — Auth middleware

The next commit makes the authentication token useful for future requests.

## 7. Why middleware?

We do not want to repeat this in every protected controller:

```js
const token = req.cookies.token
const decoded = jwt.verify(token, process.env.jwt_secret)
const user = await User.findById(decoded.userId)
```

Imagine repeating that in:

```text
POST /posts
DELETE /posts/:id
POST /comments
POST /follow
GET /feed
```

That is duplicated security logic.

Instead, Express middleware gives us a shared checkpoint.

The route becomes:

```js
userRoutes.get(
    '/me',
    isAuthenticated,
    getUser
)
```

The sequence is:

```text
request
  |
  v
isAuthenticated
  |
  +--> authentication failed -> stop
  |
  v
getUser
  |
  v
response
```

## 8. Adding `next`

The earlier middleware signature did not accept `next`.

It changes from:

```js
const isAuthenticated = async (req, res) => {
```

to:

```js
const isAuthenticated = async (req, res, next) => {
```

Why?

Because authentication is a **checkpoint**, not the final response.

When authentication succeeds:

```js
next()
```

means:

> This request passed this middleware. Continue to the next handler.

## 9. The authentication middleware

The project has:

```text
backend/middlewares/authMiddleware.js
```

and the implementation is:

```js
import jwt from 'jsonwebtoken'
import User from '../models/user.model.js'

const isAuthenticated = async (req, res, next) => {
    try {
        const token = req.cookies.token

        if (!token) {
            res.status(404).json({ message: "No token Found" })
        }

        const decoded = jwt.verify(token, process.env.jwt_secret)
        const user = await User.findById(decoded.userId)

        if (!user) {
            res.status(404).json({ message: "User Not found" })
        }

        req.user = user
        next()
    } catch (error) {
        return res.status(500).json({ message: "Server Error" })
    }
}
```

There are four major responsibilities:

```text
1. Read token
2. Verify token
3. Load user
4. Attach user to request
```

## 10. `jwt.verify()` is the critical operation

We use:

```js
const decoded = jwt.verify(
    token,
    process.env.jwt_secret
)
```

It is important to distinguish **decode** and **verify**.

Decoding simply reads token data.

Verification checks the token cryptographically and validates its claims such as expiration.

For authentication decisions, trust must be based on **verification**, not on an unverified decoded payload.

## 11. Loading the user from MongoDB

After verification:

```js
const user = await User.findById(decoded.userId)
```

This is a deliberate architectural choice.

JWT answers:

> Which identity did the server issue this credential for?

MongoDB answers:

> What is the current state of that user?

This matters because profile data can change after the token is issued.

## 12. The most important line: `req.user = user`

We attach authenticated identity to the request:

```js
req.user = user
```

Then the downstream controller can simply do:

```js
export const getUser = (req, res) => {
    res.status(200).json(req.user)
}
```

The controller no longer needs to understand JWT.

It does not need to parse cookies.

It does not need to run `jwt.verify()`.

It does not need to query the user again.

The authentication middleware established the request context.

### Real-life analogy

Think of entering an office.

Security checks your ID at the gate.

After verification, the receptionist receives:

```text
Visitor = Mrinal
```

The receptionist does not scan your ID again.

That handoff is what `req.user` represents.

# Part 4 — Cookies

## 13. The practical browser problem

We now have a JWT. But where should the browser keep it so that future requests can carry it?

One option for browser-based authentication is a cookie.

Our controller does:

```js
res.cookie("token", token, cookieOptions)
```

and later middleware reads:

```js
const token = req.cookies.token
```

That creates the full transport loop.

## 14. Cookie lifecycle

The browser receives something conceptually like:

```http
Set-Cookie: token=...
```

and stores it in its cookie jar.

Later:

```http
Cookie: token=...
```

is sent on requests that match the cookie policy.

So:

```text
Server
  -> Set-Cookie
  -> Browser cookie jar
  -> future request
  -> Cookie header
  -> Server
```

## 15. `cookie-parser`

The backend imports:

```js
import cookieParser from "cookie-parser";
```

and installs:

```js
app.use(cookieParser())
```

This makes cookies conveniently available as:

```js
req.cookies
```

Therefore:

```js
req.cookies.token
```

gives the JWT value from the incoming cookie.

## 16. `HttpOnly`

Our cookie options currently contain:

```js
const cookieOptions = {
    httpOnly: true,
}
```

`HttpOnly` means normal browser JavaScript cannot read that cookie using APIs such as `document.cookie`.

That reduces the ability of injected JavaScript to directly steal the cookie value.

But it is important not to overclaim:

> HttpOnly helps protect the credential from direct JavaScript access. It does not prevent XSS itself, and it does not automatically solve CSRF.

A malicious script running inside your origin may still be able to issue authenticated requests from that browser context even if it cannot read the cookie value.

## 17. SameSite

We also discussed cookie settings such as:

```js
sameSite: 'lax'
```

`SameSite` controls when browsers attach cookies in cross-site situations.

Common modes are:

- `Strict` — most restrictive
- `Lax` — practical default for many session patterns
- `None` — allows cross-site cookie sending and requires `Secure`

Treat it as browser policy, not as a magic security switch.

## 18. Secure

Another flag is:

```js
secure: true
```

It tells the browser to send the cookie only over secure HTTPS connections.

A production authentication cookie should normally use HTTPS and `Secure`.

So keep this mental model:

```text
HttpOnly -> JavaScript cannot read cookie
Secure   -> cookie only sent over secure transport
SameSite -> control cross-site cookie sending
```

Each solves a different part of the problem.

# Part 5 — The complete request flow

## 19. Login request

The client sends:

```http
POST /users/login
Content-Type: application/json
```

with:

```json
{
  "email": "user@example.com",
  "password": "correct-password"
}
```

The controller:

```js
const userExists = await User.findOne({ email })
```

then verifies the password:

```js
const correctPassword = bcrypt.compareSync(
    password,
    userExists.password
)
```

then creates the JWT:

```js
const token = genToken(userExists._id)
```

then sets the cookie:

```js
res.cookie("token", token, cookieOptions)
```

The browser stores that cookie.

## 20. Protected `/users/me` request

Later the browser calls:

```http
GET /users/me
Cookie: token=...
```

Express has already registered:

```js
app.use(cookieParser())
```

The router resolves:

```js
userRoutes.get('/me', isAuthenticated, getUser)
```

Middleware executes:

```js
const token = req.cookies.token
```

then:

```js
const decoded = jwt.verify(
    token,
    process.env.jwt_secret
)
```

then:

```js
const user = await User.findById(decoded.userId)
```

then:

```js
req.user = user
```

then:

```js
next()
```

and finally:

```js
res.status(200).json(req.user)
```

So the entire authentication pipeline is:

# Part 6 — Bugs and better practices

## 21. Missing `return` after sending errors

Current code has:

```js
if (!token) {
    res.status(404).json({ message: "No token Found" })
}
```

But execution can continue afterward.

A better implementation is:

```js
if (!token) {
    return res.status(401).json({
        message: 'Authentication required'
    })
}
```

The same principle applies to the `!user` branch.

## 22. Better status codes

The current middleware uses `404` for missing authentication.

A more precise model is:

```text
401 -> authentication missing or invalid
403 -> authenticated but not allowed
404 -> requested resource does not exist
```

## 23. Do not return password hashes

The current controller returns user objects directly:

```js
res.status(200).json(newUser)
```

and:

```js
res.status(200).json({
    message: "Login Successfull",
    user: userExists,
})
```

Because the Mongoose user object includes `password`, this can leak the bcrypt hash to the frontend.

A safer approach is to explicitly create a public representation.

```js
const sanitizeUser = (user) => ({
    id: user._id,
    name: user.name,
    username: user.username,
    email: user.email
})
```

Then return only that representation.

## 24. Prefer async bcrypt comparison

The current login code uses:

```js
bcrypt.compareSync(password, userExists.password)
```

A Node.js server generally benefits from using the asynchronous API in request handling:

```js
const correctPassword = await bcrypt.compare(
    password,
    userExists.password
)
```

The reason is that synchronous work can block the event loop and reduce the server's ability to process other requests while the password computation is running.

## 25. Cookie configuration for production

The classroom code starts with:

```js
const cookieOptions = {
    httpOnly: true,
}
```

A more production-oriented version might be:

```js
const cookieOptions = {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'lax',
    path: '/'
}
```

The exact SameSite and cross-origin configuration depends on deployment architecture.

If the frontend and backend are on different sites, CORS and credential configuration must be considered together with cookie attributes.

## 26. Debugging cookies

When:

```js
req.cookies.token
```

is `undefined`, debug in this order:

```text
1. Did the login response contain Set-Cookie?
2. Did the browser accept the cookie?
3. Is the domain correct?
4. Is the path correct?
5. Is Secure preventing HTTP usage?
6. Is SameSite affecting the request?
7. Is the frontend using credentials: 'include' when needed?
8. Is backend CORS configured for credentials?
9. Is cookie-parser installed before the route?
10. Is the cookie expired?
```

Do not immediately assume JWT is broken.

## 27. Logout

The repository literally leaves a homework marker:

```js
// HW - Log out
```

The basic browser-side logout operation is:

```js
res.clearCookie('token', cookieOptions)
```

But understand the security nuance:

> Clearing the browser's cookie does not automatically invalidate a copy of the JWT that an attacker may already have stolen.

This leads naturally to refresh-token rotation, server-side sessions, token versioning or explicit revocation mechanisms in stronger systems.

# Part 7 — Authentication vs authorization

Do not mix these.

### Authentication

> Who are you?

Example:

```text
JWT -> userId -> user exists
```

### Authorization

> Are you allowed to perform this action?

Example:

```js
user.role === 'admin'
```

So later we can compose middleware like:

```js
router.delete(
    '/users/:id',
    isAuthenticated,
    isAdmin,
    deleteUser
)
```

Authentication establishes identity. Authorization decides permissions.

```text
backend/
├── controllers/
│   └── user.controllers.js
├── middlewares/
│   └── authMiddleware.js
├── models/
│   ├── post.model.js
│   └── user.model.js
├── routes/
│   └── user.routes.js
├── utils/
│   └── genToken.js
├── index.js
├── package.json
└── .env
```

### What each folder does

**routes/** answers: which endpoint and middleware chain should handle this request?

**middlewares/** answers: what must happen before the final controller?

**controllers/** answers: what should this endpoint actually do?

**models/** answers: how is persistent data represented and queried?

**utils/** contains reusable helpers such as JWT generation.

This is separation of concerns. The goal is not “more folders”; the goal is making responsibilities obvious.
