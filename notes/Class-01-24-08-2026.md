## What we were solving today

Today we started with one of the most important backend security questions: **what exactly should the server store when a user gives us a password?**

The wrong answer is the plaintext password. If our database is leaked, every password becomes immediately usable. The right mental model is that the server should be able to **verify** a password without keeping a readable copy of it.

## 1. Hashing vs encryption

Encryption is reversible with a key. Password hashing is designed to be one-way.

```text
Encryption:
plaintext -> encrypt + key -> ciphertext
ciphertext -> decrypt + key -> plaintext

Password hashing:
password -> hash -> stored representation
```

For login, we do not decrypt the stored hash. We take the password the user just entered and use bcrypt verification against the stored hash.

The key idea is:

> We do not need to recover the password. We only need to answer whether the supplied password matches.

## 2. Why not use a normal fast hash?

Password attacks are fundamentally guessing attacks. If an attacker steals a password database, they can test candidate passwords offline.

For password storage we therefore want an algorithm that is deliberately expensive to compute. Bcrypt is designed for password hashing and includes a salt and configurable computational cost.

## 3. What is a salt?

Suppose two users choose the same password:

```text
hello123
```

Without a salt, a deterministic hash gives the same result every time.

With a unique salt:

```text
hello123 + salt A -> hash A
hello123 + salt B -> hash B
```

This prevents a database from trivially revealing that multiple accounts use the same password and makes large precomputed tables much less useful.

A salt is not a secret key. Its job is to make each password hash unique and to make precomputation less effective.

## 4. Bcrypt in this project

The backend depends on bcrypt:

Our code uses ES modules:

```json
"type": "module"
```

so imports look like:

```js

```

### Salt generation

The class introduced:

```js
const salt = await bcrypt.genSalt(10)
```

The `10` is the bcrypt cost setting used in our example. It is better to think of it as a computational-cost parameter than as “run the password through a simple transformation exactly ten times.”

## 5. The important bcrypt detail

Our registration implementation eventually uses:

```js
const hashedPassword = await bcrypt.hash(password, 10)
```

and stores:

```js
const newUser = await User.create({
    username,
    name,
    password: hashedPassword,
    email
})
```

The flow is:

```text
password entered by user
        |
        v
bcrypt.hash(password, cost)
        |
        v
bcrypt encoded hash
        |
        v
MongoDB
```

### Important classroom observation

The code also creates:

```js
const salt = await bcrypt.genSalt(10)
```

but does not use that variable in the subsequent hash call.

So that explicit `salt` variable is redundant in the current implementation.

You can either write:

```js
const salt = await bcrypt.genSalt(10)
const hashedPassword = await bcrypt.hash(password, salt)
```

or use the simpler approach:

```js
const hashedPassword = await bcrypt.hash(password, 10)
```

For this project, the second version is clearer.

## 6. What is actually stored?

A bcrypt encoded string commonly looks conceptually like:

```text
$2b$10$...
```

The string encodes the bcrypt version, cost setting, salt and derived value according to bcrypt's format.

This is why we normally do **not** need a separate database column for the bcrypt salt when using the standard bcrypt API.

## 7. Login verification

On login, our project uses:

```js
const correctPassword = bcrypt.compareSync(
    password,
    userExists.password
)
```

We do not try to decrypt the stored value and we should not manually recreate a hash string by guessing how bcrypt is internally formatted.

Conceptually:

```text
login password
      |
      v
bcrypt.compare(...)
      |
      +--> read verification information from stored bcrypt hash
      |
      +--> perform bcrypt computation
      |
      v
   true / false
```

The stored hash contains enough information for bcrypt to perform the comparison.

## 9. Registration flow in the project

The controller extracts:

```js
const { name, username, email, password } = req.body
```

then validates required fields, checks for an existing username/email, validates the password, hashes it, and creates the user.

The overall sequence is:

```text
POST /users/register
        |
        v
extract req.body
        |
        v
validate input
        |
        v
check username/email
        |
        v
bcrypt hash
        |
        v
User.create()
```

This is the foundation for the authentication system we build in later classes.

## 10. Real-life analogy

Think of a hotel storing a transformed version of a room-access secret instead of keeping a notebook containing everyone's actual secret.

The front desk does not need to know the original secret in readable form. It needs a mechanism that can confirm whether what you entered matches the secure representation.

The bcrypt hash is that representation; the salt makes each stored representation unique; the cost makes guessing more expensive.

## 11. Production improvements

### Never log plaintext passwords

Do not do:

```js
console.log(password)
```

### Never return password hashes to clients

The current controller returns the Mongoose user object directly in registration/login responses. That can expose the `password` field unless we deliberately sanitize it.

A safer API response is:

```js
const userResponse = {
    id: user._id,
    name: user.name,
    username: user.username,
    email: user.email
}
```

### Prefer async bcrypt APIs in request handlers

Blocking password operations synchronously can reduce Node.js throughput. In later improvements, prefer:

```js
const correctPassword = await bcrypt.compare(
    password,
    userExists.password
)
```
